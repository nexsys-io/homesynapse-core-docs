# AMD-97: First-Class Device-Level Confirmation Characterization

**What it adds.** Confirmation semantics previously lived only at the capability level (Doc 02 §3.6 per-capability `ConfirmationMode`; §3.8 `Expectation` → `CONFIRMED`/`NOT_YET`/`FAILED`; adapters could override only the tolerance band). There was no slot for whether a *specific real device* can render a true `CONFIRMED` at all. AMD-97 adds that slot — additively, extending the reserved per-device-override seam (Doc 08 §3.6 `DeviceProfile`), not superseding any Locked contract.

## The applied edits

1. **Doc 08 §3.6** — the `confirmation[]` block: **eight fields** (`capability`, `confirmationMode`, `authoritativeAttribute`, `reportsAuthoritative`, `reportingPosture`, `confirmability`, `recommendedTimeoutMs`, `degradeRule`) + corpus-level `provenance` metadata in the bench serialization. Review edits folded: the field count stated explicitly (the dispatch said "seven" while listing eight); `degradeRule` is an **enum** (`NO_REPORT_TIMEOUT_TO_UNCONFIRMED | NACK_TO_FAILED | IMMEDIATE_UNCONFIRMED | CONFIRM_FROM_CACHE_OR_READBACK`, free-text in a `notes` sibling only); the **measured taxonomy split** (bench E5-#5) carried by `confirmability × reportsAuthoritative` — "attribute never reported" (`READBACK_ONLY`, the Hue `color_loop_active` class → readback-`BEST_EFFORT`) vs "no attribute" (`NONE`, the `identify` class → strict `UNCONFIRMABLE`) — without a fourth verdict value. Measured worked example embedded (Hue 5-block + SNZB empty); live values pointer: `nexsys-bench/corpus/`. Engine-consumption caveats recorded (idempotent confirm-from-cache/readback; settled-value tolerance; superseded-expectation expiry; ingestion dedup).
2. **Doc 02 §3.8** — the per-device **confirmability** override prose (override scope widens from tolerance to confirmability; engine consumes it to choose real-CONFIRMED-attempt vs honest immediate UNCONFIRMED with the reason recorded — INV-SA-03; the ±1-mired measured validation of `TOLERANCE ±50K`).
3. **Doc 16 §4** — the bundled V1 read-API-subset recording note (frozen v1.1 `NonFiringVerdict` = a distinct V1 vocabulary, NOT a value-subset of `SuppressionReason`; deferred-not-contradicted).
4. **Register** — **AMD-97-INV-01** (§51): *a command whose confirmation is `DISABLED`/`UNCONFIRMABLE` never renders `CONFIRMED`.* No existing invariant covered this (source-verified); it pins the moat's honesty guarantee at the device level, composing with AMD-90-INV-01 (per-action, no engine retry), AMD-95 (`DISABLED` ≡ optimistic, now with a recorded honest reason), AMD-87-INV-01 (Expectation codec round-trip), and INV-SA-03 (never-silent degrade). Enforced structurally today by the M7.5a registry-free read-path derivation (a `DISABLED` command is never ledger-tracked → no `state_confirmed` → no `CONFIRMED`); M9's confirmation-acceptance tests pin the device-level half on the captured fixtures.

## Consumption contract (M9 acceptance)

A `CONFIRMABLE` device's hero command yields a true `CONFIRMED` on the captured fixture; an `UNCONFIRMABLE`/`BEST_EFFORT` path yields an honest `UNCONFIRMED` — never a false positive. Per-capability timeouts are measured necessities (OnOff/Level ~0.5 s vs CT 6.7–8.4 s on the same device). The corpus latency bands are **reference-stack-conditioned** (captured under ZHA's reporting configuration, which differs from Doc 08 §3.7 defaults) — M9 acceptance pins Configure-Reporting as an explicit step and either re-measures under its own §3.7 posture or records config parity; the corpus `on_off` samples are ACK→report, `brightness`/`color_temperature` are command→report (pin the reference point in the acceptance harness).
