## §1 — The locked text this amends (quoted at `homesynapse-core-docs` `055832c`)

**Doc 06 §3.6, the ERROR paragraph (`:225`):** *"**ERROR.** A specific configuration value is invalid, but the rest of the configuration is usable. Examples: negative integer where a positive integer is required, string value where an enum is expected, value outside the declared `minimum`/`maximum` range. The affected key reverts to its JSON Schema default value. A `ConfigIssue` record is retained. A `config_error` diagnostic event is produced for each ERROR-severity issue (…). The dashboard displays a persistent notification identifying the key, the invalid value, and the applied default. On startup, ERROR issues allow the process to start (exit code 0, but with warnings logged). On reload, ERROR issues cause the reload to be rejected entirely; a partially corrected configuration is never applied."*

**Doc 06 §3.6, the WARNING paragraph (`:227`):** *"**WARNING.** The configuration is valid but contains something worth noting. Examples: deprecated key (still functional, scheduled for removal per INV-CS-06), unknown key (possible typo — detected because JSON Schema uses `additionalProperties: false` on known sections), value near the boundary of its valid range. No value is changed. The issue is logged and surfaced in the dashboard."*

**Doc 06 §3.6, the startup-permissive sentence (`:229`):** *"At startup, the system is more permissive because there is no prior good state to preserve — ERROR keys revert to defaults, and the system starts in a degraded-but-functional state."* — and the CLI exit-code sentence (`:231`): *"1 (errors present — system would start but with defaults applied)"*.

**Doc 06 §4.5 (`:394–:416`):** *"The Configuration System produces one event per ERROR-severity validation issue at startup."* — the payload: `"path"`, `"severity": "ERROR"`, `"message"`, **`"applied_default": 90`**, `"trigger": "startup"`.

**Doc 06 §6.5 (`:527–:533`):** *"**Impact:** FATAL issues prevent startup. ERROR issues cause the affected keys to revert to schema defaults; the system starts with those defaults applied. WARNING issues are logged. **Recovery:** … (for ERROR) the default that was applied."*

**Doc 12 (the line reading, grep `Non-fatal validation errors`; `:483` at the hub's read):** *"Non-fatal validation errors → affected keys revert to defaults, WARNING logged, startup continues."*

## §1b — ADDENDUM at the one-way-door review (2026-10-09 ~15:0x CT; after the word) — the principle and the invariant the rule reverses, not quoted at ratification; **Nick's second word GIVEN 15:03 CT: `rec: P4-ratified` — "the reversal stands with §1b's reason" — with three reads at the bytes folded below (§1c)**

The independent review (F-§4) found two locked sentences the ratified text did not quote and that say the OPPOSITE of R-A at startup:

**Doc 06 §1 P4 (`:31`):** *"**P4: Validation is comprehensive, not fatal.** A typo in a retention threshold should not prevent lights from turning on. The validation pipeline collects all issues and classifies them by severity. Fatal errors (corrupt YAML, broken secret references) prevent startup. Non-fatal errors (invalid value for one key) cause that key to revert to its schema-defined default while the rest of the system starts normally (INV-RF-06, INV-HO-04)."*

**Doc 06 §5 C5 (`:487`):** *"| C5 | INV-RF-06 (graceful degradation — at startup; strict atomicity — on reload) |"* — and `config/configuration/MODULE_CONTEXT.md:181`: *"**INV-RF-06** Graceful degradation. On startup, ERROR keys revert to defaults (system starts degraded). On reload, ERROR causes full rejection (preserves prior good state)."*

The reason the reversal stands (the hub's recommendation): P4's premise is a household whose lights depend on a boot that must succeed unattended. The run's Pi is deployed by an attended card that reads the boot line and rolls back by sha (R-E); a boot that REFUSES naming the key costs one attended minute, while a boot that starts "normally" with a silently dropped key (the IR-61b case: no staleness at all, one `config_error` line nobody reads — and at a failed boot the event is dropped anyway, F10) is the run's record lying about what ran. P4's second sentence is re-cut, not struck: *"A typo in a retention threshold must not go unnoticed: the boot refuses, naming the key, and the operator corrects it before anything runs (AMD-102)."* INV-RF-06's startup clause is superseded ("strict at startup and on reload; the difference is only what is preserved"); its reload clause stands. INV-HO-04 (named beside it) is read by DOCS-2 before its row moves. The WARNING tier has NO producer at `37f05a9` after this unit (the only WARNING arm was the unknown key); "a deprecated key stays WARNING" in §5 below is design text until a deprecation arm exists — DOCS-2 says so in the fold.

### §1c — Nick's three reads at `rec: P4-ratified` (15:03 CT; verbatim in the v101 DR D-v101-31), folded into the fold
1. **The governance invariant is NOT what is reversed.** `governance/Architecture_Invariants_v1.md:308` INV-RF-06 is about subsystem partial failure — "when a subsystem or integration is degraded, the rest continues at full capability"; its test is crashing the Zigbee adapter or the automation engine; it says nothing about configuration keys reverting to defaults. That reading is Doc 06's own (P4 `:31`; C5's row `:487`; `config/configuration/MODULE_CONTEXT.md:181`). **AMD-102 amends Doc 06's P4 and C5's APPLICATION of INV-RF-06 to configuration keys; the governance text is untouched** — DOCS-2's fold says exactly that, so no later reader thinks an invariant moved. (§1b's "INV-RF-06's startup clause superseded" reads accordingly: the clause is Doc 06's, not the register's.)
2. **R-D's removals are safe for every install that exists, not only the rig.** The `.deb` ships no configuration YAML — `distribution/deb/debian/conffiles` lists only `/etc/homesynapse/homesynapse.env` — and no tracked YAML at `37f05a9` carries `permit_join_duration`, `mains_timeout_minutes` or `battery_timeout_hours`. A fresh-card install (PKG-FRESH-1, Sunday) upgraded to the CONFIG-ERROR-1 sha (UPGRADE-1, Nov 10–11) cannot trip on them. **R-E's "empty at the Pi" extends to "empty at the package."**
3. **The one real cost, owned as a row — DEPRECATE-1.** After this unit the WARNING tier has no producer, so there is no graceful path for a future key removal across an upgrade: the next removed key is a boot failure in every house that wrote it — the "monthly breaking changes" failure Doc 06 §4 exists to prevent. P4's household premise is wrong for the run and pilot zero (attended installs, rollback by sha) and right for a house on apt. So the condition, not a block: **DEPRECATE-1** — an `x-deprecated` schema annotation that classifies WARNING at startup and tolerates the key until the next major — is named now (register IR-141) as the post-run row that is a PRECONDITION for the first key removal that reaches an installed house; R-D's three are exempt by (2). **Until DEPRECATE-1 lands, the freeze list's rule is: no key leaves a schema fragment after the run.** The re-cut P4 sentence stands: a refused boot that names the key is INV-HO-04's self-explaining error; a boot that silently drops a key is the run's record lying.
