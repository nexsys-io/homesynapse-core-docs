Give the promised third-party future a **reserved architecture instead of an implicit hope — without building any of it in V1.** This doc's job is done if a future SDK, marketplace, or dynamic-loading milestone is an **additive activation of seams reserved here — never a re-architecture, and never a Groovy→Edge-class forced migration** for third parties who built against the frozen SPI (L-12: ecosystem-killing migrations share a signature — kill date before replacement parity; L-13: when a platform breaks its extension layer, the community's exit is real and permanent).

## 2. Design principles

1. **Core never depends on extensions.** HomeSynapse Core boots, runs, and passes CI with the third-party extension set empty. Extension code is never load-bearing for a core feature. (EXT-INV-1 candidate, §6. Evidence: L-1 — unsandboxed in-process extension code turns any extension bug into a platform-wide compromise; L-27 — platforms whose community code became load-bearing could not evolve without breaking users.)
2. **Capability is declared, not discovered.** An extension's full surface — events published, operations exposed, services required, config schema version, isolation level — is static manifest data validated before load, never granted at runtime undeclared. (EXT-INV-2 candidate, §6. Evidence: L-5 — moving capability from imperative code into declarative, reviewable data is the most-repeated trust win in the field; L-7.)
3. **Trust is tiered, never binary — and never over-claimed.** A graded isolation ladder (§3.3), each rung claimed only once built. **The honesty rule (ruled, DP-18-B): no sandbox or isolation language in any external copy before the enforcing rung exists.** (Evidence: L-2 — process isolation buys crash/perf containment, not privilege separation; L-4 — the honest small-team posture is no-sandbox-stated-plainly + third-party code off by default; L-6.)
4. **Data-first extensibility before code extensibility.** The profile/converter/blueprint channel — declarative artifacts through a staging-area pipeline — is the widest, safest on-ramp, and it ships value before any code-plugin machinery exists. (Restates D5 adapt-the-data. Evidence: L-22 — the staging-area model is the strongest anti-rot pattern for data-driven extensions: 5,473 devices on bus-factor ~1.5.)
5. **Breaking changes are a contract.** Notice + automated migration + a parallel old path, never a kill date before parity. This is LTD-16's deprecation discipline extended to the extension surface, and the anti-SmartThings pledge expressed as mechanism. (Evidence: L-11 — breaking changes are survivable with long notice, automated migration, parallel old-line maintenance; L-12.)

**Standing constraint (ruled 2026-07-03, DP-18-C — binds this doc and every dependent surface):** **community-contributed content is never paywalled.** NexSys monetizes trust, convenience, certification, and cloud — the hosted/verified/one-click *channel* — never *access* to community content. The repository stays free and sideloadable. (Evidence: L-24 — no surveyed platform vendor-paywalls community content; L-25 — certification programs monetize trust by binding a commercial badge to a public quality ladder.)

## 3. Architecture of the readiness

### 3.1 The frozen SPI is the plugin contract (restated, not owned here)

The extension contract already exists and is frozen: the two types a third party implements (`IntegrationFactory` → `IntegrationAdapter`) plus the declared `IntegrationDescriptor` surface (requiredServices, dataPaths, configSchemaMajor/Minor, isolationLevel — the AMD-54..64 freeze), composed statically at the composition root (LTD-17). LTD-17's own text is the reservation's anchor: *"The API boundary is the investment; the loading mechanism is swappable."* Nothing in this doc redesigns that contract; every seam below is an activation path for it. Integration-API compatibility is versioned independently of the product (LTD-16 / INV-CS-04) — the compat-range primitive §4 row 6 builds on.

### 3.2 The seam classes, named as one direction

Seven seams (§4 table): dynamic loading · the integration operation registry · event-manifest layering · the trust-boundary ladder · namespace & identity governance · packaging & distribution · the marketplace trust floor. Individually these are gaps the assessment inventoried (§2); named together they are the single direction "third-party code and data, adopted without re-architecture." V1 builds none of them. What V1 already provides is the substrate that makes them cheap later: a frozen narrow SPI (§3.1), per-module event-class manifests (M3.6c), a built-but-unwired `SchemaRegistry.registerIntegrationSchema`, a reserved `InvokeIntegrationAction` permit, and the `IsolationLevel.RESERVED_SUBPROCESS` enum slot (AMD-63's deliberate purchase).

### 3.3 The trust-boundary ladder (four rungs, in order) — and the honesty rule

1. **Scoped context wrappers** — enforce LTD-17's isolation intent at the object-capability level (today `EntityRegistry`/`StateQueryService` are injected unscoped; the wrapper narrows what an adapter can see to its own integration scope).
2. **Publish permissions** — enforce the descriptor's declared event surface (the permitted-publish-types check; today a full `EventPublisher` is injected).
3. **Resource quotas** — INV-RF-02's reserved path; caps are **designed, user-visible quotas, never discovered mystery limits** (L-23).
4. **`RESERVED_SUBPROCESS`** — process isolation for non-curated third-party code. **Ruled (DP-18-B):** wave-1 curated adapters remain `IN_JVM` behind the quality gate (the HA-core analog); `RESERVED_SUBPROCESS` is the **intended default rung for non-curated third-party code at marketplace time**.

Feasibility proof for rung 4: Homebridge retrofitted per-plugin subprocess isolation as pure configuration, zero plugin code changes, because its contract stayed process-agnostic (L-3) — our SPI's narrow two-type contract preserves exactly that property. Rungs are built in order; each is claimed externally only once it enforces (**the honesty rule, doc text per DP-18-B** — for a trust company, one over-claimed sandbox costs more than every marketing sentence it earned). R-4 backlog rows name rungs 1–4 so they are never forgotten; none gates V1.

### 3.4 The AI-authoring distribution surface

AI-authored automation components are **marketplace artifacts like any other** — no separate pipeline, no bypassed gate (L-33: no surveyed platform lets AI-authored content bypass its extension review gates). The stack, all four parts already designed or ruled: **(1)** the declarative component artifact (Doc 16 §3.2 — sealed-permit expansion, no runtime DSL) gated by AX-7 versioning (§7, DP-18-A); **(2)** the `AutomationLinter` static form-check at load (Doc 17 §3.3 E3 — malformed AI-authored components rejected before they run); **(3)** AIOT-INV-1's proposer-only frame (AI never actuates; the deterministic engine disposes); **(4)** per-version automated scanning at distribution time (§4 row 7 — the gate an AI-accelerated authorship era requires is automated, per-version, and public: L-31, L-32). No surveyed platform has all four. Claim language stays inside Doc 17 §7-6's counsel-gated boundary: state the mechanism ("statically verified, structurally proposer-only, durably auditable"), never the superlative.

### 3.5 Namespace & identity governance — **binding on M9.3**

This section exists so the identity layer is governed **before** M9.3 makes anything one-way; it is why this doc Locks first. DP-B's permanence ruling (deterministic identity derivation — a pure function of the integration type string) is safe *because* the naming layer is governed here: the rename hazard is a naming-layer problem, defused by convention, not by identity-file machinery.

- **(a) Extension identity is two-level and publisher-scoped:** `publisher.extension` (e.g. `acme.energy-meter`), immutable once published, with transfer-on-abandonment governance pre-planned (L-26 — bus-factor-1 is the default state of community infrastructure; L-28 — flat first-come naming + abandonment yields fork confusion; the mature endpoint is publisher-scoped identity + verified publishers + immutable IDs).
- **(b) Type-string namespace convention:** first-party integration types keep their existing bare names (`zigbee` — already bound by M9.2's identity derivation); the bare namespace is **reserved to first party**. Third-party integration types and profile identities are publisher-scoped per (a), immutable by convention. This convention lands as a **design constraint in the M9.3 instruction** (with the M9.2 identity binding it protects) — the profile registry must key third-party profile sources by namespaced identity from day one.
- **(c) Collision ruling (settled here):** a third-party extension may shadow a first-party capability/profile **only with explicit user consent, flagged in the UI; core wins brand preference** — the HA-sanctioned shape (L-29: collision policy must be an explicit ruling, not an accident of load order).
- **(d) Profile/device identity disambiguation:** fingerprint-priority matching with explicit precedence + rebrand (white-label) mapping (L-30 — fingerprints outrank model strings at data scale; Tuya generic-modelIDs are the stress case). **Folds into the M9.3 instruction as a design constraint** (assessment R-2), alongside the registry non-preclusion note: `DeviceProfile`'s Zigbee vocabulary must be explicitly Zigbee-scoped-with-a-general-seam-note (or protocol-namespaced) so it never silently becomes the generic profile contract, and the third-party-profile **data channel** (user-override precedent) stays first-class.

## 6. Invariants — two candidates through the minting test; three principles kept unminted

The test (the register's own, from the Doc 16 INV-SA minting + the INV-GA-02 near-duplicate warning, applied at the Doc 17 Lock): a candidate is minted first-class only if it **adds a constraint its cited parents do not already impose** and cites those parents.

- **EXT-INV-1 — Core Never Depends on Third-Party Extensions (candidate; recommend MINT at Lock).** HomeSynapse Core boots, runs, and passes CI with the third-party extension set empty; no core feature may take a load-bearing dependency on any extension-supplied capability, type, or event. *Parents:* **INV-RF-01** (integration crash isolation — binds failure propagation), **INV-LF-02** (no outbound dependence — binds the network direction), **LTD-17** (static composition — binds the build graph). *Novel:* the parents bind runtime failure, network direction, and compile-time dependency direction; **none binds the load-bearing-ness of the third-party actor class as such** — a statically-compiled, crash-isolated extension could still become a dependency core features assume (the SmartThings/webCoRE failure: L-1, L-13, L-27; HA's surviving counter-shape: community code is an "optional addition… at the cost of stability" — L-17, L-18). *CI-testable now:* the composition root builds and boots with zero non-first-party integrations — the M9.1 fake-adapter path already approximates the harness.
- **EXT-INV-2 — Extension Capability Is Declared, Not Discovered (candidate; recommend MINT at Lock).** Every third-party extension declares its full capability surface — event classes published, operations exposed, services required, config schema version, isolation level — in static manifest data validated before load; no capability is granted at runtime that was not declared. *Parents:* the frozen **`IntegrationDescriptor`** (AMD-54..64: requiredServices, dataPaths, configSchemaMajor/Minor, isolationLevel), the **M3.6c per-module event-class manifests**, **AMD-55-INV-01** (lifecycle-hook surface discipline on the same freeze). *Novel:* the descriptor exists, but nothing binds the third-party actor class to declared-capability-only — today a full `EventPublisher` is injected and the permitted-publish-types check is unbuilt (assessment §2: trust boundary paper-only). *CI-testable when rung 2 lands:* manifest-vs-behavior test + permitted-publish-types enforcement. *Evidence:* L-5, L-7 (Chrome's manifest-as-trust-contract and remote-code ban; VS Code's declarative contribution points).
- **Kept as principles, NOT minted:** **(a)** *"The frozen SPI is the plugin contract, additive-only"* — fully carried by the AMD-54..64 freeze + AMD-55-INV-01 + LTD-16/INV-CS-04; minting would create the droppable near-duplicate INV-GA-02 warns against. **(b)** *"Trust is tiered, never binary"* — testable content lands only as ladder rungs are built; premature minting is the AIOT-INV-2/3 precedent (kept as principle until enforceable). **(c)** *"Data-first extensibility"* — owned by D5's ruling; this doc restates.

## 7. Decisions — four SETTLED at authoring; open items marked

**SETTLED (ruled by Nick 2026-07-03, beat 57 — full verbatim rationale: `nexsys-hivemind/context/handoff/pm-handoff.md` beat-57 rulings record; indexed in `context/process/decision-rationale-index.md`):**

1. **DP-B — deterministic integration identity is PERMANENT policy.** Restart- and reinstall-stable pure function of the type string; no identity file to back up, corrupt, or crypto-shred. The rename hazard is a naming-layer problem **§3.5 defuses before M9.3 makes anything one-way** — that sequencing is this doc's Lock-before-M9.3 obligation. M9.3 device adoption is identity-ungated.
2. **DP-18-A — AX-7 direction RATIFIED:** semver on `(componentId, version)` + declared compat range + forward-only non-destructive migration (AMD-93-aligned) + a **named deprecation floor**; strict whole-definition immutability rejected (L-14 — it appears nowhere at ecosystem scale). One ruling unlocks both futures: community-shared components AND AI-as-author (Doc 17 §7-4 sequences AX-7 ahead of any AI-authoring milestone). **The formal AMD lands with this doc's Lock docs pass** (Doc 16 OQ2 owns the mechanism). **Floor quantification — OPEN for Nick's co-sign: proposed N = 6 release cycles with a Repairs-class automated-migration surface** (the HA ADR-0021 shape, L-11; never below LTD-16's one-major-version floor).
3. **DP-18-B — the isolation line RATIFIED:** wave-1 curated `IN_JVM` behind the quality gate; `RESERVED_SUBPROCESS` = the intended default rung for non-curated third-party code at marketplace time (AMD-63 bought the slot for exactly this); **the no-sandbox-claims honesty rule is doc text** (§2 principle 3, §3.3).
4. **DP-18-C — RULED (a):** community content is never paywalled — stated as this doc's standing constraint (§2). Revenue re-homes to the hosted/verified/one-click channel: **monetize trust, not access.** The Connect-line reword rides this doc's Lock docs pass (strategy + governance coherent in one commit); exact wording polishes at pricing time.
