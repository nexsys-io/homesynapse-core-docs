**Q3 — The M4.0b-2 one-shot backfill (the hardest detail).** Now pinned to source:
- *Where the rule re-derives on replay:* `processBatch` (the intended REPLAY/catch-up path; presently exercised only by the contract test — `StateProjection.java:451-454` notes "future bus wiring") calls `rule.evaluate(ctx)` at `:483`; `onEvent` does so at `:373`. In both, derived drafts are applied to state **only** inside the `mode == LIVE` block (`:518` / `:408`).
- *Where reconciliation is detected:* `initialize()` `:549` (`persistedVersion != projectionVersion` → `clear()` + `cursorPosition=0`).
- *The hook:* the backfill = "during the reconciliation REPLAY, also apply the buffered re-derived drafts to in-memory state (still without publishing)." Concretely a flag set in `initialize()` when reconciliation fires, consulted in the `processBatch`/`onEvent` apply path to extend `applyToState` to derived drafts while `mode != LIVE`.
- *The gate (one-shot):* AMD-41 §3.2.4 serializes reconciliation metadata into the checkpoint blob. **[Pass-2 correction — see §G.0]** The fields **already exist in source** as `CheckpointData.reconciledAt`/`reconciledFromVersion`/`reconciledToVersion` (`CheckpointData.java:45-47`) and are (de)serialized by `CheckpointSerializer`. What is *not* yet wired is **population**: `SqliteStateStore.serializeCheckpoint(int)` currently passes `serializer.serialize(snapshot, projectionVersion, null, null, null)` (`:188`), and the `StateCheckpointSource.serializeCheckpoint(int)` interface only accepts `projectionVersion`. Gate the backfill on the **`1→2`** transition (the pre-M4.0b log has zero `state_changed`, so no logged-vs-derived double-apply exists); on any later replay, logged `state_changed` already exists and would be applied as inbound (+1), so re-deriving-and-applying would double-count `stateVersion`. **Dependency to surface:** M4.0a must extend the `serializeCheckpoint` path so the projection *populates* `reconciledFromVersion=1`/`reconciledToVersion=2` on the 1→2 reconciliation (OR-M3-13). M4.0b's backfill gate then reads that metadata. (Note the source field names are `reconciledFromVersion`/`reconciledToVersion`, not AMD-41 §3.2.4's `fromVersion`/`toVersion`.)
- *The governance gap (highest-value finding):* AMD-41 §3.2.4 step 3 states the projection "emits derived events only after exiting REPLAY." The backfill introduces a **new replay-time in-memory state mutation** that the ratified execution model does not describe. It does not publish/write events (so the single-writer / no-writer-in-REPLAY invariant is intact), but it still needs an **amendment refining AMD-41 §3.2.4** to authorise the one-shot in-memory backfill on the version-transition reconciliation. The plan calls the backfill "settled" but never flags that it amends AMD-41. Add this AMD to the M4 amendment set (and to the P2 renumbering).
- *The test (plan §8, sharpened):* (i) after a 1→2 reconciliation, historical attributes reconstruct from the `state_reported` log; (ii) `stateVersion` equals the count of processed events (no double-increment); (iii) a *second* restart at code-version 2 finds persisted-version 2 → **no** reconciliation → backfill does **not** run; (iv) a hypothetical 2→3 bump applies logged `state_changed` (+1) without the backfill re-applying. Research 9 will additionally settle replay wall-time vs the 5s Pi budget and snapshot-store activation — fold into §4.4/§9 when it lands.
