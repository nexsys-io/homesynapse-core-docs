## §2 — Decision Point Analysis

### DP-1: Infrastructure vs callback failure distinction

**Question:** When a subscriber's read operation fails due to SQLite infrastructure issues (`SQLiteException`, `IOException`, `OutOfMemoryError`), should the supervisor treat this differently from a user-callback exception?

**Source text quoted:**

AMD-42 §3.4.5 (lines 61–64):
> "The supervisor wraps `subscriber.onEvent(envelope)` calls in a try/catch: [...] On exception: append to the subscriber's in-memory DLQ ring (cap 1024); persist to `subscriber_dead_letters` (per AMD-36 — note that AMD-36 has no `status` column; row presence IS the parked state); increment `crashCount` within the rolling 10-minute window; schedule retry via the bus's shared `ScheduledExecutorService` with backoff `MIN = 3s, MAX = 30s, jitter = 0.2`. After 5 retries (AMD-36 default) OR `crashCount >= 5` within 10 minutes, the circuit breaker trips: `mode → SUSPENDED`, emit CRITICAL on health channel `subscriber.<id>.suspended`."

PLAN §4 (lines 595–777): No mention of exception-type distinction. The contract test `supervisorCatchesSubscriberException()` (line 697) tests generic exceptions.

AMD-36 (lines 12–129): The DLQ schema records `cause_class` and `cause_message` but the park-and-advance mechanism treats all exceptions identically.

**Resolution status:** GENUINELY OPEN.

AMD-42 §3.4.5 says "On exception" with no type qualification. The same backoff/crash-count/DLQ path applies to all exceptions. Neither the plan nor AMD-36 introduces a distinction.

**Options:**

1. **Uniform treatment (status quo).** All exceptions follow the same 3s/30s/0.2 backoff → 5-crash circuit-breaker path. Simplest to implement. Risk: a transient `SQLITE_BUSY` burns through the crash budget on retries that would succeed after a brief pause.

2. **Infrastructure carve-out (PM recommendation).** `SQLiteException`, `IOException`, `OutOfMemoryError` → immediate SUSPENDED without burning backoff attempts. Rationale: Akka Persistence's `BackoffSupervisor.onStop` carve-out (research note §B.3) exists for exactly this reason — persistence failures stop the actor rather than throw, so the `onFailure` supervisor doesn't work. HomeSynapse's analogue: infrastructure failures indicate systemic issues (disk full, connection corruption) where retrying the same event won't help.

3. **Infrastructure fast-backoff.** Infrastructure exceptions get a shorter crash window (e.g., 3 crashes / 1 min → SUSPENDED) while callback exceptions keep 5/10min. Middle ground.

**Industry precedent:** Akka publishes the carve-out explicitly: persistence-failure causes stop, not throw, requiring `Backoff.onStop` (research note §B.3). This is the strongest published precedent for distinguishing failure types in an event-sourced subscriber.

**HomeSynapse constraints:** AMD-42 is silent on exception types. Adding a carve-out does not *contradict* AMD-42 (which says "On exception" — a carve-out for specific exception types is a refinement, not a contradiction), but it does extend beyond what AMD-42 specifies. The M3.1 Cowork prompt could implement this as an implementation decision within the `SubscriberSupervisor` without requiring a new amendment, since AMD-42 §3.4.5 delegates supervisor implementation details.

**Recommendation:** Option 2 (infrastructure carve-out). The supervisor should catch infrastructure exceptions (`SQLiteException`, `IOException`, `Error` subclasses) and transition immediately to SUSPENDED with a distinct health channel message (`subscriber.<id>.infrastructure_failure`), bypassing the DLQ and crash-window machinery. Rationale: DLQ-parking an infrastructure exception is semantically wrong — the event itself isn't poison; the infrastructure is broken. The Akka precedent is directly applicable.

**Note:** This does NOT require a new amendment. AMD-42 §3.4.5's "On exception" is implementer-directed; the supervisor's internal exception-routing logic is an implementation decision within the M3.1 scope. The M3.1 Cowork prompt should specify the exception taxonomy.

### DP-3: SubscriberInfo.mode() mechanism

**Question:** AMD-42 §3.4.1 says mode is exposed "via `SubscriberInfo.mode()`." But SubscriberInfo is a 3-field immutable record. How is mode exposed?

**Source text quoted:**

AMD-42 §3.4.1 (line 27):
> "Every subscriber registered with `EventBus` exposes a mode in `{ COLD, REPLAY, TRANSITION, LIVE, SUSPENDED }` via `SubscriberInfo.mode()`."

PLAN §4.3 (lines 654, 665–671):
> `SubscriberSnapshot subscriberInfo(String subscriberId);`
>
> ```java
> public record SubscriberSnapshot(
>     String subscriberId,
>     SubscriberMode mode,
>     long checkpoint,
>     int dlqDepth,
>     int crashCount
> ) {}
> ```

PLAN §4.2 (line 614):
> "**MODIFY** — extend the existing `SubscriberInfo` record (or replace with an interface, decision recorded in completion report) to expose `mode()`, `checkpoint()`, `dlqDepth()`, `crashCount()` for operator introspection."

PLAN §4.7 (line 745):
> "the new shape MUST include `mode()`, `checkpoint()`, `dlqDepth()`, `crashCount()` accessors or there must be a separate `SubscriberSnapshot` record (the §4.3 example uses the snapshot record approach)."

SubscriberInfo.java (lines 39–43): Confirmed 3-field record: `subscriberId`, `filter`, `coalesceExempt`.

**Resolution status:** PARTIALLY RESOLVED.

**Analysis:** There is a genuine tension between AMD-42 §3.4.1's "via `SubscriberInfo.mode()`" wording and the plan's `SubscriberSnapshot` approach. However, the plan explicitly acknowledges this tension and offers two paths:

- **Path A:** Extend `SubscriberInfo` (or replace with an interface) to add `mode()`, `checkpoint()`, `dlqDepth()`, `crashCount()`.
- **Path B:** Keep `SubscriberInfo` as the 3-field registration descriptor and introduce `SubscriberSnapshot` as a separate read-only introspection type returned by `EventBus.subscriberInfo(id)`.

The plan's §4.3 code example uses Path B (SubscriberSnapshot). The plan's §4.7 says "Coder picks but reports the choice."

**Recommendation:** Path B (SubscriberSnapshot). Rationale:

1. `SubscriberInfo` is a registration-time descriptor. Mode, checkpoint, dlqDepth, and crashCount are runtime-state fields that change continuously. Mixing static registration metadata with volatile runtime state in one type violates single-responsibility.
2. `SubscriberInfo` is used in `EventBus.subscribe(SubscriberInfo)` — callers construct it. Adding mode/checkpoint fields that callers cannot set creates an asymmetric API.
3. The plan's §4.3 example is the most concrete specification and uses SubscriberSnapshot.
4. AMD-42 §3.4.1's "via `SubscriberInfo.mode()`" can be read as "via a subscriber-info-like accessor" rather than "via the `SubscriberInfo` record literally." The plan's `EventBus.subscriberInfo(id) → SubscriberSnapshot` satisfies the intent.

The M3.1 Cowork prompt should specify Path B and note the AMD-42 wording tension in its completion report.

### DP-4: Per-subscriber dedicated read connection model

**Question:** INV-SUB-ISO-02 requires one read connection per subscriber, but the read pool default is 2 (AMD-27). How do 4+ subscribers each get a dedicated connection?

**Source text quoted:**

INV-SUB-ISO-02 (Architecture Invariants §19, lines 1049–1051):
> "Each subscriber holds one SQLite read connection for the lifetime of its subscription. The connection is allocated from the persistence layer's read executor pool (AMD-27) at `subscribe()` time and is released at `unsubscribe()` or on a SUSPENDED → resume cycle. No two subscribers share a read connection at any instant. **The mechanism for binding 'one connection per subscriber' against a read-pool size that may be smaller than the subscriber count is an M3.1 design decision (open question 20.2 of the top-down analysis).**"

Persistence MODULE_CONTEXT (line 103):
> "Configurable thread count via constructor (`AMD-27` default is 2; rejects `< 1`)."

AMD-27 (full text): Specifies the platform-thread executor pattern but does not specify pool sizing beyond the default. No discussion of subscriber-count scaling.

PLAN §4 (lines 595–777): Does not specify the connection-allocation mechanism for subscribers. The file list (§4.2) does not mention changes to the persistence module.

**Resolution status:** GENUINELY OPEN.

The invariant itself (INV-SUB-ISO-02) explicitly calls this out as "an M3.1 design decision (open question 20.2)." The plan is silent on it.

**Options:**

1. **Enlarge the shared read pool.** Set `readThreadCount = max(2, subscriberCount)` at startup. Subscribers bind to pool threads round-robin. Pros: minimal structural change. Cons: hard-coded at startup; adding subscribers at runtime requires pool resizing or pre-allocation.

2. **Per-subscriber single-thread executor (PM recommendation).** Each subscriber gets its own platform thread + connection, independent of the shared read pool. The shared pool stays at 2 for ad-hoc reads (EventStore queries, checkpoint reads). Pros: clean isolation, dynamic subscriber addition. Cons: N additional platform threads per N subscribers (acceptable on Pi 5 at expected subscriber counts of 3–6; a Pi 4's 4 cores can handle this).

3. **Connection-per-subscriber with shared thread pool.** Subscribers each own a dedicated `Connection` object but submit work to a shared platform-thread pool. The connection is bound via `ThreadLocal` for the duration of each read operation. Pros: fewer threads than option 2. Cons: connection-thread affinity is sqlite-jdbc's invariant — a connection used from multiple threads requires external serialization, which reintroduces contention.

**Industry precedent:** OTP's "one process per actor with private state" (research note §A.6) and Akka's actor encapsulation both assign private resources per isolation unit. The research note's VT-Iso + Conn-Iso anchors directly map to this.

**HomeSynapse constraints:** INV-SUB-ISO-02 says "No two subscribers share a read connection at any instant." This rules out option 3 if the shared pool size < subscriber count (connections would need to time-share). Option 2 (dedicated thread + connection) is the cleanest satisfaction of the invariant.

**Recommendation:** Option 2 (per-subscriber single-thread executor). Each subscriber's `SubscriberRuntime` owns one platform thread (`hs-sub-read-<subscriberId>`) and one dedicated SQLite read connection. The shared `ReadExecutor` pool (AMD-27 default 2) remains for non-subscriber reads (EventStore queries from API handlers, checkpoint reads, etc.). This requires no change to AMD-27's scope — the per-subscriber connections are a new resource created by the bus, not an expansion of the existing pool.

**Amendment impact:** This does NOT require a new amendment. INV-SUB-ISO-02 already mandates per-subscriber connections and explicitly defers the mechanism to M3.1. The Cowork prompt should specify the mechanism. However, the M3.1 implementation will need to add a `requires com.homesynapse.persistence` (or similar) to the event-bus module-info if the bus directly opens connections — see §6 (Additional Concerns).

### DP-5: EventBus introspection method names

**Question:** The event-bus MODULE_CONTEXT mentions four new methods: `subscribeRuntime`, `resume`, `subscriberInfo`, `subscribers`. Are these locked by the plan? Should `subscribeRuntime` coexist with `subscribe`?

**Source text quoted:**

PLAN §4.3 (lines 633–658):
```java
public interface EventBus {
    // ── Existing Phase 2 contract (preserved) ──
    void subscribe(SubscriberInfo subscriber);
    void unsubscribe(String subscriberId);
    void notifyEvent(long globalPosition);
    long subscriberPosition(String subscriberId);

    // ── New in M3.1 ──
    void subscribeRuntime(SubscriberInfo info, Subscriber runtime);
    void resume(String subscriberId);
    SubscriberSnapshot subscriberInfo(String subscriberId);
    java.util.List<SubscriberSnapshot> subscribers();
}
```

PLAN §4.3 note (lines 619–620):
> "**Note on the existing `Subscriber` vs `SubscriberInfo` split.** The Phase 2 design used `SubscriberInfo` as a registration descriptor and assumed subscriber callback behavior was supplied implicitly [...]. M3.1 makes the runtime callback explicit by introducing `Subscriber` (the `onEvent` / `onCaughtUp` callback interface). This is a small but important contract addition; the prompt MUST be explicit about it."

PLAN §4.7 (lines 736–738):
> "The complete `EventBus` interface signature (§4.3), with the explicit instruction '**Do NOT add a `publish()` method.**'"

Event-bus MODULE_CONTEXT "Amendments in force" (line 84):
> "The `EventBus` interface gains `subscribeRuntime`, `resume`, `subscriberInfo`, `subscribers` introspection — but does NOT gain a `publish()` method"

**Resolution status:** PARTIALLY RESOLVED.

**Analysis:** The plan's §4.3 is the definitive specification for M3.1 method names. The four new methods are specified with exact signatures and return types. The plan explicitly preserves the existing `subscribe(SubscriberInfo)` alongside the new `subscribeRuntime(SubscriberInfo, Subscriber)`.

The question of whether `subscribeRuntime` should replace `subscribe` is addressed implicitly: the plan lists both methods in the interface specification (lines 636 and 648). The existing `subscribe(SubscriberInfo)` is under "Existing Phase 2 contract (preserved)." This means both coexist.

**Rationale for coexistence:** `subscribe(SubscriberInfo)` is the metadata-only registration (used by the existing InMemoryEventBus for test scenarios, and potentially by subscribers that don't need the full runtime lifecycle). `subscribeRuntime(SubscriberInfo, Subscriber)` is the runtime registration that creates the VT, connection, supervisor, etc. The plan's note (line 619) explains why both are needed.

**What remains open:** Whether `subscribe(SubscriberInfo)` should remain a no-op in the production `InProcessEventBus` (since without a `Subscriber` callback, there's nothing to invoke), or whether it should throw `UnsupportedOperationException`. The plan does not specify this. The M3.1 Cowork prompt should.

**Recommendation:** Keep both methods per the plan's specification. In `InProcessEventBus`, `subscribe(SubscriberInfo)` should register the subscriber for filter evaluation and checkpoint tracking (preserving the Phase 2 contract) but should NOT create a VT or supervisor (since there's no `Subscriber` callback to wrap). This preserves backward compatibility with the existing `InMemoryEventBus` test fixture pattern.

## §3 — Q-Resolution Verification

### Q1: How does HomeSynapse exit SUSPENDED?

**PM's claim:** "AMD-42 §3.4.5 specifies `EventBus.resume(subscriberId)` — clears crash window, transitions SUSPENDED→REPLAY, re-attempts delivery."

**Source text (AMD-42 §3.4.5, line 65):**
> "`EventBus.resume(subscriberId)` clears the crash window, transitions SUSPENDED → REPLAY (re-bootstrap from last checkpoint), and re-attempts delivery."

**Verdict:** CONFIRMED. The source text matches the PM's claim verbatim. The exit mechanism is operator-invoked `resume()`, which clears the crash window and transitions to REPLAY from the last checkpoint.

### Q2: Crash counting vs failure rate

**PM's claim:** "HomeSynapse counts crashes, not rates — the OTP model. 5 crashes on 5 events IS meaningful."

**Source text (AMD-42 §3.4.5, line 64):**
> "increment `crashCount` within the rolling 10-minute window [...] `crashCount >= 5` within 10 minutes, the circuit breaker trips"

**Verdict:** CONFIRMED. AMD-42 counts discrete crashes (not failure rate). The `crashCount` is incremented per exception, and the threshold is a count (5) within a time window (10 min), matching the OTP `intensity`/`period` model rather than the Resilience4j/Hystrix rate-based model.

### Q3: Restart checkpoint behavior

**PM's claim:** "Crashed subscriber restarts from COLD→REPLAY from its last persisted checkpoint, not from zero unless checkpoint is missing or projectionVersion mismatches."

**Source text (AMD-42 §3.4.5, line 65):**
> "transitions SUSPENDED → REPLAY (re-bootstrap from last checkpoint)"

**Source text (AMD-42 §3.4.2, line 40):**
> "The bus reads the subscriber's persisted checkpoint (via `CheckpointStore`), opens the subscriber's dedicated read connection (§3.4.4), and begins delivering events from `checkpoint + 1` forward"

**Source text (AMD-41 §3.2.4, lines 41–44):**
> "When the projection observes `projectionVersion(persisted_checkpoint) ≠ projectionVersion(current_code)`, the projection enters a reconciliation pass: [...] the projection discards the checkpoint, resets its in-memory state to empty, and replays from `position = 0`"

**Verdict:** CONFIRMED. Resume goes SUSPENDED → REPLAY from last checkpoint. Replay-from-zero occurs only on projectionVersion mismatch (AMD-41 §3.2.4). The PM's claim is accurate.

### Q4: Park-and-advance atomicity

**PM's claim:** "AMD-36's park-and-advance atomicity resolves this. The event IS delivered for INV-BUS-01 purposes; the failure is recorded in the DLQ; the checkpoint advances past it."

**Source text (AMD-36, lines 96–109):**
> "When a subscriber parks an event, two operations must be atomic:
> 1. INSERT into `subscriber_dead_letters` (park the event)
> 2. UPDATE `subscriber_checkpoints` (advance past the parked event)
>
> If the checkpoint advances but the DLQ INSERT fails, the event is silently lost — the subscriber has moved past it and no record exists. This violates the 'event is NOT lost' guarantee."

**Source text (AMD-36, lines 28–31):**
> "After N failed processing attempts for a single event, a subscriber MAY park the event in the dead-letter queue and advance its checkpoint. The event is NOT lost — it is durably recorded in the DLQ"

**Verdict:** CONFIRMED. AMD-36 specifies that parking and checkpoint-advance are atomic. The event is considered "delivered" (the checkpoint advances), and the failure is durably recorded. This resolves the exactly-once question: a DLQ-parked event counts as delivered for INV-BUS-01 purposes because (a) the subscriber processed it (attempted N times), and (b) the failure record is durable.

### Q6: ReplayWindowQueue overflow behavior

**PM's claim:** "ReplayWindowQueue overflow means slightly longer catch-up, not data loss. The subscriber pulls from EventStore in LIVE mode regardless."

**Source text (AMD-42 §3.4.2, line 42):**
> "Events newly published during REPLAY are captured in the subscriber's `ReplayWindowQueue` (bounded at 10000) and drained in TRANSITION."

**Source text (PLAN §4.4, line 710):**
> "`replayWindowOverflowAt10000IsCriticalAlert()` — M3.2 placeholder"

**Source text (INV-SUB-ISO-05, line 1061–1063):**
> "One `ReplayWindowQueue` per subscriber (lifetime: REPLAY entry → drain complete). Garbage-collected after LIVE transition."

**Verdict:** PARTIALLY CONFIRMED. AMD-42 §3.4.2 specifies the queue is bounded at 10000 but is **silent on what happens at overflow**. The plan's §4.4 includes a test method `replayWindowOverflowAt10000IsCriticalAlert` as an M3.2 placeholder, suggesting the design intent is to emit a CRITICAL alert on overflow — but this is not specified in the amendment text. The PM's claim that "the subscriber pulls from EventStore in LIVE mode regardless" is correct in the LIVE steady state, but the overflow behavior during REPLAY/TRANSITION is genuinely unspecified. This is an M3.2 concern, not M3.1.

### Q7: Thread safety of mode reads

**PM's claim:** "All subscriber work happens on the subscriber's VT (INV-SUB-ISO-01). The mode AtomicReference provides happens-before via volatile read."

**Source text (INV-SUB-ISO-01, line 1047):**
> "The subscriber's virtual thread is the only thread that invokes `subscriber.onEvent(envelope)`; the per-subscriber `SubscriberSupervisor` wraps these invocations."

**Source text (INV-SUB-ISO-04, lines 1057–1059):**
> "Each subscriber's mode [...] is held in a per-subscriber `AtomicReference<SubscriberMode>`. Transitions are atomic (CAS-based). [...] The mode is observable to operators through the bus's introspection API."

**Source text (PLAN §4.4, line 685):**
> "`modeReferenceIsAtomicAcrossConcurrentObservers()` — multiple threads reading `subscriberInfo(id).mode()` concurrently see consistent values."

**Verdict:** CONFIRMED. INV-SUB-ISO-01 confirms single-VT for `onEvent`. INV-SUB-ISO-04 confirms `AtomicReference` with CAS transitions. `AtomicReference.get()` is a volatile read in the Java Memory Model, providing happens-before with respect to the most recent `set()` or successful `compareAndSet()`. The plan's contract test (line 685) explicitly tests cross-thread mode reads. The design does not need an additional memory-ordering note — `AtomicReference` already provides the required guarantees.

### Q8: SelfProducedFilter bypass and reset on restart

**PM's claim:** "AMD-41 §3.2.2 specifies filter is bypassed during REPLAY/TRANSITION. A new SelfProducedFilter instance is created empty on LIVE transition."

**Source text (AMD-41 §3.2.2, line 37):**
> "During `SubscriberMode.REPLAY` and `SubscriberMode.TRANSITION` (AMD-42 §3.4.1), `isSelfProduced()` returns `false` unconditionally. Replay must re-derive deterministically from the log; the in-memory filter from the previous process is gone and cannot be trusted."

**Verdict:** PARTIALLY CONFIRMED. The bypass during REPLAY/TRANSITION is explicitly specified. However, AMD-41 does NOT explicitly say "a new SelfProducedFilter instance is created empty on LIVE transition." The source says the filter "returns `false` unconditionally" during REPLAY/TRANSITION, which could mean either (a) the existing instance has a mode-aware `isSelfProduced()` that short-circuits, or (b) the instance is replaced. The PM's claim of a *new* instance is an inference, not a source-verified fact. The M3.1 implementation may choose either approach — the behavioral contract is the same.

### Q9: Fallback behavior

**PM's claim:** "No Hystrix-style fallbacks. The staleness model (EntityState.staleAfter + stale derived at read time) IS the fallback behavior."

**Source text (AMD-42, full text):** No mention of "fallback" anywhere in AMD-42.

**Source text (state-store MODULE_CONTEXT, line 46):**
> "`EntityState` | record (9 fields) | [...] `staleAfter` (Instant, **nullable**), `stale` (boolean, derived at read time)."

**Source text (state-store MODULE_CONTEXT, line 94):**
> "`EntityState.stale` is derived at read time. When `staleAfter` is non-null, `stale = Instant.now().isAfter(staleAfter)`. When `staleAfter` is null, `stale` is always `false`."

**Verdict:** CONFIRMED. AMD-42 is silent on fallbacks — there are no Hystrix-style fallback mechanisms. The `EntityState.staleAfter` and `stale` fields exist with the described semantics (nullable `Instant`, boolean derived at read time). The staleness model is the implicit "fallback" behavior: when a subscriber is SUSPENDED and state becomes stale, downstream consumers see `stale = true` and can degrade gracefully (e.g., REST API returns the stale state with a warning header). This is a read-side concern, not a bus-side concern.

## §4 — Anti-Pattern Coverage Matrix

Assessment of each of the 15 anti-patterns from the research note's cross-system synthesis against the committed design.

| # | Anti-pattern | Status | Citation |
|---|---|---|---|
| 1 | Restart-storm without a give-up threshold | ADDRESSED | AMD-42 §3.4.5: 5 crashes / rolling 10 min → SUSPENDED. |
| 2 | Restart-storm with a too-tight threshold | ADDRESSED | AMD-42 §3.4.5: 10-minute window is well above the OTP "don't go below 30s" guidance. 5/600s ≈ 1 restart per 2 minutes sustained. |
| 3 | Blocking the event loop / dispatcher | ADDRESSED | INV-SUB-ISO-01 (per-subscriber VT), AMD-26/27 (platform-thread executors for SQLite), LTD-11 (no `synchronized`). A blocking subscriber stalls only its own VT. |
| 4 | Closing over actor state in a Future callback | NOT APPLICABLE | HomeSynapse uses virtual threads, not actor message-passing with futures. The per-subscriber VT model doesn't have the same closure-over-state hazard because there's no dispatcher reassignment. |
| 5 | Chained ask patterns with per-stage timeouts | NOT APPLICABLE | HomeSynapse's bus is notification-only (no ask/tell). No chained request-response patterns exist in the subscriber model. |
| 6 | Misconfigured circuit breaker as outage amplifier | ADDRESSED | AMD-42 §3.4.5: SUSPENDED requires operator intervention (no automatic probe). This is the conservative choice that avoids the "outage amplifier" failure mode. INV-BUS-03 ensures one subscriber's circuit trip doesn't affect others. |
| 7 | Stuck-in-HALF_OPEN under low traffic | ADDRESSED | HomeSynapse has no HALF_OPEN state. SUSPENDED is terminal until operator invokes `resume()`. The Resilience4j #903/#1389 stuck-HALF_OPEN issue cannot occur. |
| 8 | Hystrix thread-pool starvation from non-interruptible HTTP clients | PARTIALLY ADDRESSED | Per-subscriber VT model avoids shared thread pools. However, sqlite-jdbc's JNI calls are non-interruptible (they pin the platform thread). A subscriber stuck in a long SQLite read cannot be cancelled via `Thread.interrupt()`. Mitigation: platform threads are per-subscriber (DP-4 recommendation), so starvation is subscriber-local. |
| 9 | `/deadLetters` as application DLQ | ADDRESSED | AMD-36 introduces a first-class, schemed, durable DLQ (`subscriber_dead_letters` table). No reliance on debug-level dead-letter mechanisms. |
| 10 | At-least-once delivery without idempotent receivers | ADDRESSED | INV-ES-05 mandates subscriber idempotency. INV-BUS-01 specifies exactly-once delivery during normal operation. Crash recovery uses checkpoint-based resume with at-least-once semantics requiring idempotent receivers. |
| 11 | Retry storms across layers | PARTIALLY ADDRESSED | AMD-42 §3.4.5's backoff (3s/30s/0.2 jitter) prevents per-subscriber retry storms. However, the interaction between subscriber-level retries and DLQ-level retries (AMD-36 default 5 attempts) is specified as a single path — retry at the supervisor level, then park. No stacked retry concern exists because there is only one retry layer. The "PARTIALLY" is because the spec doesn't explicitly state "retry only at one layer." |
| 12 | Too many ActorSystem instances per JVM | NOT APPLICABLE | HomeSynapse is a single-process, single-bus architecture. No multiple bus instances. |
| 13 | Stateless actors | NOT APPLICABLE | HomeSynapse subscribers are stateful by design (mode FSM, checkpoint, DLQ, self-filter). The anti-pattern targets Akka's actor model. |
| 14 | Mutable message payloads | ADDRESSED | `EventEnvelope` is an immutable record (INV-ES-01). `SubscriberInfo` is an immutable record. All bus-level types are records or interfaces with no mutation paths. |
| 15 | `ConfigEntryNotReady` raised from wrong level | NOT APPLICABLE | HomeSynapse doesn't use Home Assistant's config-entry model. The subscriber registration API (`subscribe`/`subscribeRuntime`) is synchronous and doesn't have a tiered setup path. |

**Summary:** 8 ADDRESSED, 2 PARTIALLY ADDRESSED, 5 NOT APPLICABLE, 0 NOT ADDRESSED.

## §5 — Practice Adoption Matrix

Assessment of each of the 12 practices from the research note's "Practices worth considering" section.

| # | Practice | Status | Citation |
|---|---|---|---|
| 1 | Restart with bounded intensity over a period | ALREADY ADOPTED | AMD-42 §3.4.5: 5 crashes / rolling 10 min → SUSPENDED. Directly mirrors OTP `intensity`/`period`. |
| 2 | Exponential backoff with multiplicative jitter | ALREADY ADOPTED | AMD-42 §3.4.5: MIN=3s, MAX=30s, jitter=0.2. Matches Akka's `BackoffSupervisor` worked example exactly. |
| 3 | Stash messages during recovery, drain after | ALREADY ADOPTED | AMD-42 §3.4.2: ReplayWindowQueue (bounded at 10000) captures events during REPLAY, drained in TRANSITION. HomeSynapse's bound is explicit; Akka's stash is unbounded. |
| 4 | One supervisor per logical resource | ALREADY ADOPTED | AMD-42 §3.4.5: per-subscriber `SubscriberSupervisor`. INV-BUS-03 + INV-SUB-ISO-01..06 formalize the per-subscriber isolation. |
| 5 | Separate composable concerns | ALREADY ADOPTED | The bus is notification-only (no publish); persistence is via EventPublisher; supervision is per-subscriber; DLQ is per-subscriber; rate-limiting is per-subscriber (AMD-43 §3.6.4). Each concern is a separate component. |
| 6 | Distinguish failure-rate from failure-count thresholds | ALREADY ADOPTED | AMD-42 §3.4.5 uses crash-count (not rate), matching OTP. The research note confirms count-based is appropriate for low-traffic subscribers where statistical significance of rates is questionable. |
| 7 | Single-writer invariant for event-sourced entities | ALREADY ADOPTED | INV-WRITER-01, AMD-26. All writes route through a single `WriteCoordinator` platform thread. |
| 8 | Death-watch separate from supervision | WORTH DELIBERATING | AMD-42 specifies supervision (restart/suspend) but does not specify a separate "watch" mechanism for lifecycle visibility. The plan's `subscriberInfo(id)` and `subscribers()` introspection methods partially fill this role. However, there is no asynchronous "subscriber terminated" signal analogous to Akka's `Terminated`. For M3.1, the introspection API is likely sufficient; an event-based lifecycle notification could be valuable for M3.3 observability. |
| 9 | Operator-mediated reset for hard failures | ALREADY ADOPTED | AMD-42 §3.4.5: SUSPENDED requires `EventBus.resume(subscriberId)`. No automatic probe. Matches Polly's `Isolate()/Reset()` pattern. |
| 10 | Background tasks tied to entry lifecycle | ALREADY ADOPTED | INV-SUB-ISO-01: per-subscriber VT created on subscribe, terminated on unsubscribe. AMD-42 §3.4.4: all per-subscriber resources (VT, connection, DLQ, mode ref, replay queue, self-filter) have subscriber-scoped lifetimes. |
| 11 | Statistical-significance guard before tripping | WORTH DELIBERATING | AMD-42 §3.4.5 uses crash-count (5) in a 10-min window without a `minimumNumberOfCalls` guard. For a subscriber processing 1 event/hour, 5 crashes could accumulate faster than 5 successes, tripping the breaker on a near-zero success sample. However, the research note's own analysis (Q2) acknowledges this is intentional for the count-based model: counting crashes (not rates) already implies a known denominator. The design decision to count crashes rather than rates implicitly addresses this — but the M3.1 Cowork prompt should document the rationale explicitly. |
| 12 | Journal-failure carve-out | WORTH DELIBERATING | Research note §B.3: Akka Persistence requires `Backoff.onStop` because persistence failures stop the actor. This is directly relevant to DP-1 (infrastructure vs callback failure distinction). If adopted per DP-1 recommendation, this practice is covered. |

**Summary:** 8 ALREADY ADOPTED, 3 WORTH DELIBERATING, 1 NOT APPLICABLE (none), 0 DEFERRED.

## §6 — Additional Concerns Surfaced

### 6.1 JPMS module-info changes required by M3.1

**File:** `homesynapse-core/core/event-bus/src/main/java/module-info.java` (lines 1–13)

The current module-info declares:
```
module com.homesynapse.event.bus {
    requires transitive com.homesynapse.event;
    exports com.homesynapse.event.bus;
}
```

M3.1 introduces types that may need additional JPMS dependencies:

- `SubscriberSupervisor` uses a `ScheduledExecutorService` and `Clock` — both are in `java.base`, so no new `requires`.
- `SubscriberDlq` needs to persist to `subscriber_dead_letters` — if this persistence call routes through the persistence module's `WriteCoordinator`, the event-bus module may need `requires com.homesynapse.persistence;` or a new interface in `event-model` that the bus depends on transitively. The plan's §4.2 does not call out a module-info change.
- `InProcessEventBus` needs `EventStore` for pull-based reads — `EventStore` is in `com.homesynapse.event` (already transitively required). No new `requires`.
- Per-subscriber SQLite read connections (DP-4): if the bus directly opens connections via `DatabaseExecutor`, it needs access to the persistence module's internal types. However, the plan's ArchUnit rule `EVENT_BUS_DOES_NOT_IMPORT_SQLITE_DRIVER` (§4.5, line 722) says: "no class in `core/event-bus` imports `org.sqlite.*` or `java.sql.Connection` directly." This means the bus must receive connections through an adapter interface, not import JDBC directly.

**Concern:** The M3.1 Cowork prompt must specify how the per-subscriber read connection is provided to the bus without violating the `EVENT_BUS_DOES_NOT_IMPORT_SQLITE_DRIVER` ArchUnit rule. The likely mechanism: the bus receives a `Supplier<Connection>` or a `ReadExecutor` factory from the wiring layer (`homesynapse-app`). The module-info may need `requires com.homesynapse.persistence;` or the connection factory must be defined in `com.homesynapse.event` (event-model) to keep the dependency graph clean.

### 6.2 `Subscriber` interface name — potential collision check

**File:** Plan §4.2 (line 608): "NEW — `Subscriber.java`"

The plan introduces `com.homesynapse.event.bus.Subscriber`. A search of the codebase is warranted to ensure no existing type named `Subscriber` exists in other modules that could cause import ambiguity. The current module has no type named `Subscriber`. The `InMemoryEventBus.java` test fixture uses `Consumer<Long>` for callbacks, not a `Subscriber` type. No collision found in the event-bus module. The M3.1 Cowork prompt should verify no collision exists in downstream modules via grep at prompt generation time.

### 6.3 SubscriberSnapshot fields vs AMD-42 §3.4.1

**File:** Plan §4.3 (lines 665–671)

The plan specifies `SubscriberSnapshot` with 5 fields: `subscriberId`, `mode`, `checkpoint`, `dlqDepth`, `crashCount`. AMD-42 §3.4.1 references `SubscriberInfo.mode()` but does not specify the other introspection fields (`checkpoint`, `dlqDepth`, `crashCount`). These fields come from AMD-42 §3.4.5 (crash count) and AMD-36 (DLQ depth) individually, but their aggregation into `SubscriberSnapshot` is a plan-level design decision, not an amendment-level specification.

**Concern:** None — the plan is the authoritative M3 implementation spec, and the fields are traceable to the amendments individually. The M3.1 Cowork prompt should cite both the plan and the relevant amendment sections for each field.

### 6.4 Contract test methods scheduled for M3.1 that depend on not-yet-defined types

**File:** Plan §4.4 (lines 682–704)

Several M3.1-active contract test methods reference types that M3.1 must create:
- `subscribeRuntimeStartsInColdMode()` depends on `SubscriberMode.COLD` (new enum)
- `INV_SUB_ISO_01_oneVirtualThreadPerSubscriber()` depends on the ability to inspect VT names
- `INV_SUB_ISO_02_oneReadConnectionPerSubscriber()` depends on "fixture introspection on the executor's slot accounting" (line 690) — this fixture introspection mechanism does not exist yet and must be designed as part of M3.1

**Concern:** The test `INV_SUB_ISO_02_oneReadConnectionPerSubscriber` (line 690) requires introspecting the read executor's slot accounting. If the per-subscriber connection model (DP-4) uses dedicated per-subscriber platform threads rather than the shared pool, the "slot accounting" introspection must be on the new per-subscriber connection infrastructure, not the existing `ReadExecutor`. The M3.1 Cowork prompt should specify how this test introspection works.

### 6.5 `subscribe(SubscriberInfo)` behavior in InProcessEventBus

**File:** Plan §4.3 (lines 636, 648)

The plan preserves `subscribe(SubscriberInfo)` alongside `subscribeRuntime(SubscriberInfo, Subscriber)`. The `InMemoryEventBus` test fixture implements `subscribe(SubscriberInfo)` as a filter-evaluation-only registration (no callback). In the production `InProcessEventBus`, the meaning of `subscribe(SubscriberInfo)` without a `Subscriber` runtime is ambiguous:

- Does it register for filter evaluation and checkpoint tracking only (passive)?
- Does it throw because production subscribers must always provide a `Subscriber`?
- Is it a deprecated legacy method?

**Concern:** The M3.1 Cowork prompt must specify the `InProcessEventBus.subscribe(SubscriberInfo)` behavior. Recommendation: passive registration (filter + checkpoint only, no VT, no supervisor). This preserves the test fixture contract while keeping `InProcessEventBus` compatible with the contract test base.

### 6.6 Plan §4.2 SubscriberInfo modification ambiguity

**File:** Plan §4.2 (line 614)

The plan says SubscriberInfo is to be "**MODIFY**ed — extend the existing `SubscriberInfo` record (or replace with an interface, decision recorded in completion report)." But the plan's §4.3 example uses `SubscriberSnapshot` as a separate type and does not modify `SubscriberInfo`. This creates a disconnect in §4.2's file list: `SubscriberInfo.java` is listed as MODIFY, but the plan's interface specification (§4.3) leaves it unchanged. The §4.7 section resolves this by making it a Coder decision. The M3.1 Cowork prompt should either lock the decision (keep SubscriberInfo as-is, use SubscriberSnapshot for introspection) or explicitly delegate it with clear constraints.
